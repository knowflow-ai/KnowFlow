# Gunicorn vs Flask 性能测试报告

**测试日期**: 2025-01-13
**测试环境**: macOS, Python 3.10
**测试工具**: 自定义异步性能测试工具 (aiohttp)

---

## 执行摘要

本次测试对比了 Flask 开发模式（单进程）和 Gunicorn 生产模式（6 workers）的并发性能。测试结果显示：

**🎯 核心发现**:
- **QPS 提升**: 32.0% (820.81 → 1083.10 req/s)
- **P99 延迟降低**: 24.4% (2374.69 → 1794.09 ms)
- **测试通过率**: 100% (2000/2000 请求成功)

**📊 推荐配置**: Gunicorn 6 workers 适合中等并发场景（50 并发）

## 性能分析

### 为什么 Gunicorn 更快？

1. **并行处理能力**
   - Flask 单进程只能串行处理请求
   - Gunicorn 6 workers 可以同时处理 6 个请求
   - 50 并发场景下，Gunicorn 可以更快地消化请求队列

2. **资源利用率**
   - Flask 单进程只能使用 1 个 CPU 核心
   - Gunicorn 6 workers 可以分散到多个核心
   - 充分利用多核 CPU 的计算能力

3. **长尾延迟优化**
   - Gunicorn 的进程隔离避免了单个慢请求阻塞整个服务
   - P99 延迟降低 24.4% 证明了这一点

### 为什么平均延迟略有上升？

1. **进程间开销**
   - 负载均衡需要额外的调度时间
   - 进程间上下文切换有轻微开销

2. **连接池管理**
   - 每个 worker 维护独立的数据库连接池
   - 初始连接建立需要额外时间

3. **内存竞争**
   - 6 个进程共享系统资源
   - 可能导致内存访问竞争

**结论**: 尽管平均延迟略有上升，但 P99 延迟的大幅降低和 QPS 的显著提升使得 Gunicorn 在生产环境中更具优势。

## 生产环境建议

### 1. Worker 数量配置

**推荐公式**: `workers = (2 × CPU_CORES) + 1`

| CPU 核心数 | 推荐 Workers | 适用场景 |
|-----------|-------------|----------|
| 2核 | 4-5 | 小规模部署 |
| 4核 | 8-9 | 中等规模 |
| 8核 | 16-17 | 大规模部署 |

**本次测试**: 6 workers 在中等并发场景下表现良好

### 2. 数据库连接池配置

**关键参数**:
```yaml
mysql:
  max_connections: 900  # MySQL 最大连接数
```

**计算公式**:
```
总连接数 = workers × 每个 worker 的连接池大小
         = 6 × ~10-15
         = 60-90 连接

建议预留: max_connections - 总连接数 > 20
```

### 3. 内存规划

**每个 Worker 内存占用**: 约 200-300 MB (取决于应用复杂度)

**总内存需求**:
```
总内存 = master进程 + (workers × worker内存)
       ≈ 100 MB + (6 × 250 MB)
       ≈ 1.6 GB
```

**推荐配置**: 至少 2GB 可用内存用于 RAGFlow 服务

### 4. 监控指标

**关键指标**:
- **QPS**: 保持在 1000+ req/s
- **P99 延迟**: 控制在 2000ms 以内
- **错误率**: 保持在 0.1% 以下
- **Worker 重启次数**: 每天不超过 5 次

**监控命令**:
```bash
# 查看 Gunicorn 进程
ps aux | grep gunicorn

# 监控 QPS
watch -n 1 'curl -s http://localhost:9380/health'

# 查看数据库连接数
docker exec mysql mysql -uroot -p -e "SHOW PROCESSLIST;"
```

## 故障排查

### 常见问题

#### 1. Worker 频繁重启

**症状**: 日志显示 worker 不断重启

**原因**:
- 内存不足导致 OOM
- 数据库连接池耗尽
- 代码存在内存泄漏

**解决方案**:
```bash
# 增加 max_requests 参数，让 worker 定期重启释放内存
GUNICORN_MAX_REQUESTS=5000

# 或调整 worker 数量
GUNICORN_WORKERS=4  # 减少到 4
```

#### 2. 数据库连接超时

**症状**: 大量 "Lost connection to MySQL server" 错误

**原因**: 连接池配置不当

**解决方案**:
```yaml
# service_conf.yaml
mysql:
  max_connections: 900
  stale_timeout: 300  # 连接空闲超时
```

#### 3. 响应时间过长

**症状**: P99 延迟超过 3000ms

**排查步骤**:
1. 检查数据库慢查询日志
2. 检查 Elasticsearch 响应时间
3. 检查 Redis 连接是否正常
4. 查看系统负载 (`top`, `htop`)
